# Умный список покупок — backend API

Бэкенд приложения для совместного ведения списков покупок с подсказками
«часто покупают вместе». FastAPI + PostgreSQL, интерактивная документация
доступна в Swagger UI на `/docs`.

## Возможности

- Личные списки покупок: товары, количество, единицы измерения, заметки,
  приоритет, отметка «куплено», произвольный порядок.
- Совместная работа: приглашение по коду (плюс QR), роли `owner` / `editor` /
  `viewer`, управление участниками, отзыв доступа.
- Подсказки «часто покупают вместе» с возможностью полного отключения.
- Каталог из ~200 продуктов с поиском по опечаткам (`малоко` → `молоко`).
- Авторизация: access-токен (JWT) + одноразовый refresh-токен, выход из
  аккаунта, список активных сессий, смена пароля.

## Запуск

```powershell
# 1. Зависимости
.\venv\Scripts\python.exe -m pip install -r req.txt

# 2. Конфигурация (если .env ещё нет)
Copy-Item .env.example .env
# заполните DB_PASSWORD и JWT_SECRET_KEY:
#   python -c "import secrets; print(secrets.token_urlsafe(48))"

# 3. Схема БД. База должна существовать, миграции применятся при старте.
.\venv\Scripts\python.exe scripts\bootstrap_db.py --dbname smart_supply_list --base-schema --migrations

# 4. Каталог товаров и стартовые правила подсказок
.\venv\Scripts\python.exe scripts\seed_catalog.py

# 5. Сервер
.\venv\Scripts\python.exe main.py
```

Документация: <http://127.0.0.1:8000/docs>

## Как пользоваться API

```powershell
# Регистрация и вход
$body = '{"email":"me@example.com","password":"StrongPass123","display_name":"Иван"}'
Invoke-RestMethod -Uri http://127.0.0.1:8000/auth/register -Method Post -ContentType application/json -Body $body

$login = Invoke-RestMethod -Uri http://127.0.0.1:8000/auth/login -Method Post `
  -ContentType application/json -Body '{"email":"me@example.com","password":"StrongPass123"}'
$H = @{ Authorization = "Bearer $($login.access_token)" }

# Список и товар — в ответе на добавление сразу приходят подсказки
Invoke-RestMethod -Uri http://127.0.0.1:8000/lists -Method Post -Headers $H `
  -ContentType application/json -Body '{"name":"Продукты","items":["хлеб"]}'
```

В Swagger UI нажмите «Authorize» и вставьте `access_token`.

## Как работают подсказки

Движок отвечает на вопрос «что обычно берут вместе с этим товаром». Работает по
трём источникам, результаты объединяются и переранжируются:

| Источник | Что это | Приоритет |
|---|---|---|
| `personal` | что именно этот пользователь покупает вместе | высший |
| `statistical` | совстречаемость по всем спискам (support / confidence / lift) | средний |
| `seed` | 173 курируемых правила, поставляются с приложением | базовый |

`seed` нужен из-за проблемы холодного старта: на пустой базе статистике не на
чем учиться, и подсказки были бы пустыми. По мере накопления данных
статистика перевешивает курируемый приор.

Обратная связь влияет на ранжирование: `POST /suggestions/feedback` с
`action=accepted` поднимает подсказку, `rejected` — опускает.

Результаты кешируются по хешу нормализованной корзины, поэтому повторный
запрос — один индексированный `SELECT` (в замерах ~2 мс против ~10–20 мс).

### Отключение подсказок

| Уровень | Как | Область |
|---|---|---|
| Пользователь | `PATCH /me/settings` → `ai_suggestions_enabled: false` | все подсказки этого пользователя |
| Запрос | `?suggest=false` при добавлении товара | один вызов |
| Сервер | `AI_SUGGESTIONS_ENABLED=false` в `.env` | всё приложение |

При выключении подсказки не вычисляются локально. Внешних вызовов нет:
всё считается по таблицам БД.

### Подсказки без LLM

Движок табличный: поиск по `product_pair_rules` (`seed` + `statistical` +
персональные совместные покупки) с переранжированием по фидбеку.
Значения `llm`/`hybrid` в `SUGGESTIONS_PROVIDER` и поля `llm_*` в API
оставлены для совместимости: они принимаются, но всегда ведут себя как
`statistical` (`llm_configured=false`, `llm_model=null`). Внешних
вызовов и ключей нет.

## Разбор ввода и пополнение (`/smart`)

| Эндпоинт | Что делает | Внешние вызовы |
|---|---|---|
| `POST /smart/parse` | Предпросмотр разбора: `«2л молока»` → название + количество 2 + единица «л». Список не меняется | нет |
| `GET /smart/replenish` | «Что скоро закончится»: медианный интервал между отметками «куплено» по каждому товару | нет |

Разбор количества из строки работает и при обычном добавлении товаров:
`POST /lists/{id}/items` с `{"name": "молоко 2л"}` создаст товар «молоко»
с количеством 2 и единицей «л». Явно переданные `quantity`/`unit` всегда
важнее разобранных. Подсказки «часто покупают вместе» возвращаются в том же
ответе на добавление (`suggestions`), отдельно их вписывать не нужно.

## Структура

```
app/
  config.py            конфигурация из .env с валидацией на старте
  core/                логирование, ошибки, JWT и пароли, нормализация, rate limit
  core/smart_parse.py  разбор «2л молока» → название + количество + единица
  db/                  пул psycopg 3 и раннер SQL-миграций
  schemas/             pydantic-модели запросов и ответов (основа Swagger)
  schemas/smart.py     схемы разбора ввода и пополнения
  repositories/        только SQL, без бизнес-правил
  repositories/smart.py — история покупок для пополнения
  services/            бизнес-логика, права доступа, движок подсказок
  services/suggestions/statistical.py  табличный движок (seed + statistics + personal)
  services/smart/      replenish.py (периодичность пополнения)
  api/                 зависимости, middleware, обработчики ошибок, роутеры
  api/routers/smart.py эндпоинты /smart/*
  main.py              сборка приложения
migrations/            001…004, применяются по порядку и отслеживаются в БД
database/database.sql  базовая схема (таблицы под миграции)
scripts/               bootstrap_db.py, seed_catalog.py
tests/                 тесты на отдельной БД
_backup_legacy/        предыдущая версия main.py / db.py
main.py                точка входа
```

Права доступа выражены в SQL: каждый запрос к списку идёт через join с
`shopping_list_members`, поэтому обратиться к чужому списку нельзя даже при
ошибке в слое сервисов. Посторонний получает `404`, а не `403` — существование
списка не раскрывается.

## Миграции

Файлы `migrations/NNN_описание.sql` применяются по возрастанию версии, каждый
в своей транзакции, отметки хранятся в таблице `schema_migrations`. Повторный
запуск ничего не меняет. Advisory-блокировка делает одновременный старт
нескольких процессов безопасным.

Отключить автоприменение: `RUN_MIGRATIONS_ON_STARTUP=false`.

## Безопасность

- Пароли: PBKDF2-HMAC-SHA256, 600 000 итераций, соль на пароль. Число итераций
  хранится внутри хеша, при повышении настройки старые пароли обновляются
  прозрачно при следующем входе.
- Одинаковый ответ и одинаковое время для неизвестного email и неверного
  пароля — существование аккаунта не определяется по отклику.
- Refresh-токены хранятся только как SHA-256 хеш и одноразовые. Повторное
  использование отозванного токена трактуется как утечка: все сессии
  пользователя отзываются.
- Активность аккаунта проверяется на каждом запросе, поэтому отключение
  пользователя действует сразу, а не после истечения JWT.
- Все SQL-запросы параметризованы, сортировка приходит только из enum.
- Заголовки безопасности, лимит размера тела, rate limit (общий и строгий для
  эндпоинтов авторизации).
- Email участников в списке виден только владельцу.
- Единый формат ошибок `{"error": {"code", "message", "details"}}`, внутренние
  детали и трассировки наружу не отдаются.

Rate limit работает в пределах процесса. При нескольких воркерах или репликах
ограничения нужно ставить на reverse-proxy или в общем хранилище.

## Заметки по совместимости

- Ссылки терминальной версии `smartsupply://share/<uuid>` и
  `smartsupply://copy/<uuid>` продолжают работать. Новый формат —
  `smartsupply://join/<код>`: код можно отозвать и ограничить по времени и
  числу использований, а UUID списка нельзя, поскольку он неизменяем.
- Формат ответов изменился по сравнению с предыдущей версией: вместо
  `{"result": {...}}` возвращаются описанные в Swagger модели.
- `sharing_settings jsonb` заменён таблицей `shopping_list_members`; данные
  перенесены миграцией `002`. Колонка оставлена и помечена как deprecated.
